# Промт: реализация сервиса «Платёж прошёл? Докажи»

Ты — опытный backend-разработчик. Реализуй небольшой, но production-grade
сервис для проведения платёжной операции через внешнего провайдера.
Ключевая ценность решения — не количество кода, а корректность в условиях
повторов, гонок, потерянных HTTP-ответов и перезапусков процесса.

## Стек

- Язык: **Python 3.14**
- Фреймворк на выбор (FastAPI/Starlette рекомендуется — async, удобная
  работа с фоновыми задачами)
- Постоянное хранилище: любое (SQLite/Postgres) — данные обязаны
  переживать перезапуск контейнера без удаления volume
- Развёртывание: Docker Compose (`candidate-service` + `provider-simulator`)

## Главный инвариант (не нарушать ни при каких условиях)

При любых повторах, конкурентных запросах, потерянных ответах и
перезапусках **одной операции соответствует не более одного платежа
провайдера**, а **финальный статус определяется только callback-квитанцией**
(успешный HTTP-ответ провайдера ничего не подтверждает, отсутствие ответа
ничего не опровергает).

## Состояния операции

| Состояние | Значение |
|---|---|
| CREATED | операция создана, отправка не запрошена |
| PROCESSING | намерение отправки надёжно сохранено, ждём результат провайдера |
| COMPLETED | провайдер подтвердил успех callback-квитанцией |
| REJECTED | провайдер подтвердил отказ callback-квитанцией |

## Обязательный API (контракт менять нельзя)

| Метод | Маршрут | Успешный статус | Назначение |
|---|---|---|---|
| GET | /health | 200 | проверка готовности |
| POST | /operations | 201 | создание операции |
| POST | /operations/{id}/submit | 202 или 200 | надёжно запланировать отправку |
| POST | /receipts | 204 | принять callback-квитанцию |
| GET | /operations/{id} | 200 | текущее состояние |
| GET | /operations/{id}/events | 200 | история переходов |

### POST /operations

```json
{
  "operationId": "operation-123",
  "amount": "1000.00",
  "currency": "RUB",
  "description": "Оплата заказа"
}
```

- `operationId` обязателен
- `amount` — положительная десятичная строка, не более 2 знаков после точки
- валюта: RUB
- повторное создание того же `operationId` → 409 Conflict
- ответ содержит как минимум: operationId, amount, currency, description,
  status="CREATED", providerPaymentId=null (доп. поля допустимы)

### POST /operations/{id}/submit

Первый вызов должен **атомарно**:
1. проверить, что статус CREATED;
2. сохранить намерение отправки в постоянном хранилище;
3. перевести операцию в PROCESSING;
4. гарантировать продолжение отправки после перезапуска;
5. вернуть 202 Accepted.

Правила:
- сам HTTP-вызов провайдера можно делать после фиксации намерения — в том
  же процессе или в фоне; **нельзя держать блокировку операции на всё
  время внешнего вызова** (callback может прийти раньше HTTP-ответа);
- повторный submit для PROCESSING/COMPLETED/REJECTED не создаёт новое
  намерение, возвращает текущее состояние с 200 OK;
- при конкурентных submit ровно один запрос создаёт намерение
  (транзакция/уникальный индекс/CAS на статус), остальные получают уже
  сохранённое состояние.

### GET /operations/{id}/events

Каждое событие — минимум:

```json
{
  "eventId": 1,
  "type": "CREATED",
  "fromStatus": null,
  "toStatus": "CREATED",
  "message": "Operation created",
  "occurredAt": "2026-07-15T12:00:00Z"
}
```

`eventId` монотонно возрастает в пределах операции. Повторная квитанция не
создаёт второй переход в то же состояние.

## Контракт вызова провайдера

Адрес — переменная окружения `PROVIDER_URL`
(в compose: `http://provider-simulator:8081`).

```
POST {PROVIDER_URL}/payments
Content-Type: application/json
Idempotency-Key: operation-123
X-Correlation-ID: operation-123

{"operationId": "operation-123", "amount": "1000.00", "currency": "RUB"}
```

- `Idempotency-Key` обязателен и равен `operationId`;
- все повторы одной операции используют один и тот же ключ и **неизменное**
  тело запроса;
- `X-Correlation-ID` = operationId, использовать в структурированных логах;
- повтор с тем же ключом возвращает тот же `providerPaymentId`, новый
  платёж не создаётся;
- 503 и сетевые ошибки → ограниченный retry с backoff и jitter, тот же
  ключ;
- после сетевой ошибки операция остаётся PROCESSING (провайдер мог уже
  принять платёж — нельзя решать за него);
- обычный успешный ответ — 202 с `providerPaymentId` и `status: ACCEPTED`;
  этот ответ **сохраняет** providerPaymentId, но **не** переводит операцию
  в финальный статус;
- если квитанция по операции уже обработана (финальный статус
  зафиксирован), поздний 202 от провайдера не должен откатывать статус
  обратно в PROCESSING.

## Обработка callback-квитанции (POST /receipts)

Симулятор шлёт:

```json
{
  "providerPaymentId": "aa5b7856-e9f2-4fd5-955b-38b1f28d9c57",
  "operationId": "operation-123",
  "result": "COMPLETED",
  "message": "Payment completed",
  "occurredAt": "2026-07-15T12:00:00Z"
}
```

Правила (обработка квитанции и переход статуса — **одна транзакция**):

- `result` ∈ {COMPLETED, REJECTED};
- квитанция может прийти раньше HTTP-ответа на запрос к провайдеру —
  в этом случае именно она устанавливает `providerPaymentId`, если он ещё
  не был сохранён;
- повтор той же квитанции → 204, без нового перехода;
- поздняя квитанция с противоположным результатом → 204, фиксируется как
  проигнорированная (например, отдельным событием в истории), финальный
  статус не меняется;
- несовпадающий `providerPaymentId` после того, как связь уже установлена
  → 409.

## Постоянство и восстановление после рестарта

- Операции, намерения отправки, providerPaymentId и история событий
  переживают удаление и пересоздание контейнера (volume не трогается).
- При старте сервис находит все операции в PROCESSING без
  зафиксированного финального статуса и продолжает отправку с тем же
  Idempotency-Key (никогда не с новым).
- Остановка процесса между "провайдер принял платёж" и "мы сохранили это
  локально" не должна приводить ко второму платежу при следующем запуске
  — это должен гарантировать неизменный Idempotency-Key + идемпотентность
  на стороне провайдера.

## Docker Compose

Нужен `compose.yaml` в корне, сервисы `candidate-service` (слушает :8080)
и `provider-simulator` (образ
`ghcr.io/fintech-dev-lab/internship-provider-simulator:v0.2.0`) в общей
сети, том для постоянного хранилища кандидата. Всё поднимается одной
командой:

```
docker compose up --build
```

## Нефункциональные требования

- ограниченный backoff с jitter на retry к провайдеру;
- структурированные (JSON) логи с полями operationId, providerPaymentId,
  номером попытки;
- метрики: количество незавершённых (PROCESSING) операций, количество
  повторов вызовов провайдера;
- тесты на конкурентность (параллельные submit одной операции) и на
  восстановление после рестарта;
- корректное (graceful) завершение фоновой обработки при остановке
  процесса — не терять и не дублировать намерения, которые ещё
  выполняются.

## Явные антипаттерны — так делать нельзя

- заглушка, которая выставляет финальный статус без реального HTTP-вызова
  к provider-simulator;
- решение, при котором для одной операции создаётся больше одного платежа
  у провайдера (даже при рестарте / гонке / потере ответа);
- удержание блокировки операции на время внешнего HTTP-вызова к
  провайдеру;
- откат операции из финального статуса обратно в PROCESSING по позднему
  ответу провайдера.
